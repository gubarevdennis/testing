# Производительность: методика, измерения, открытые дефекты

Документ фиксирует **фактически измеренные** значения. Бюджеты ТЗ (§ «Показатели скорости», D-10): ввод p95 ≤ 50 мс и p99 ≤ 100 мс для статьи 10 тыс. слов; синхронизация p95 ≤ 500 мс; 100 читателей + 20 редакторов без потери подтверждённых изменений.

**Вывод на 2026-10-23:** целостность данных под нагрузкой и в длинных сессиях подтверждена (0 потерянных символов, 0 потерянных подтверждённых правок). После устранения причин, найденных профилированием (D-34), ввод в статье 11 тыс. слов при **CPU 1×** укладывается в бюджет (p95 24–27 мс, p99 34–44 мс), документ 5 000 блоков — p95 ≈ 62 мс (было 74–86 мс в том же окне). **При замедлении CPU 4× бюджет не выполнен** (p95 73 мс, p99 104 мс; было 96 / 120 мс), поэтому R-PERF-008, AT-84, R-PERF-006/015, V17-F02 (в части p95/p99) остаются `partial`. Цифры сильно зависят от загрузки общего контейнера: тот же базовый клиент при load average 6–13 (22.10) давал p95 64 мс при 1× и 0,5–0,8 с при 4×, при load average ≈ 4–5 (23.10) — 20–32 мс и 96 мс.

## Окружение измерений (честно)

* Один контейнер: 4 vCPU Intel Xeon 2.8 GHz, общая загрузка (load average 6–13) — параллельно шли сборки и тесты других модулей. Сервер, PostgreSQL, браузер и генератор нагрузки — на одной машине.
* Chromium из Playwright, headless. Сеть — loopback (RTT ≈ 0), эталонной сети 80 мс/20 Мбит/с не было.
* Это **не** эталонный стенд из ТЗ (ноутбук 8 ГБ, отдельный сервер). Цифры ниже — верхняя оценка; на перегруженном контейнере они отражают и соседей. Поэтому в автотестах бюджеты задержки проверяются только при `KB_PERF_ENFORCE=1` (калиброванный стенд), а целостность (ни одного потерянного символа, курсор на месте) проверяется всегда.

## Методика

| Что | Как | Где |
|---|---|---|
| Задержка ввода | Для каждой клавиши: `keydown.timeStamp` (время платформенного события, включает очередь за занятым главным потоком) → следующий кадр (`requestAnimationFrame` + задача `MessageChannel`, т.е. после отрисовки). Ввод реальными событиями клавиатуры через CDP, 100 мс между клавишами (≈ 120 слов/мин), ≥ 200 замеров, p50/p95/p99/max, плюс число long tasks > 100 мс | `tests/e2e/perf-typing.spec.ts`, `tests/e2e/perf-helpers.ts` |
| Замедление CPU | `Emulation.setCPUThrottlingRate {rate: 4}` через CDP (`KB_PERF_CPU_RATE`) | там же |
| Документы | Засеваются через импорт Markdown на сервере (как у пользователя, открывающего большую страницу): статья 700 блоков / 11 090 слов; документ 5 000 блоков с таблицей 200×4 | там же |
| Целостность | После набора текст блока равен исходному + набранному **посимвольно**; позиция курсора — в конце набранного; блок не «прыгнул» (смещение < 40 px); копия сервера содержит набранное | там же |
| Длинная сессия | 100 слов с переключением жирного/курсива/подчёркивания (200 операций форматирования) + непрерывный набор строк в течение `KB_LONG_SESSION_MIN` минут; точное сравнение итогового текста, разметки и копии сервера после перезагрузки | `tests/e2e/perf-session.spec.ts` |
| Сдвиги макета | `PerformanceObserver('layout-shift')` с начала загрузки (CLS без сдвигов от ввода) | `tests/e2e/ui-p0-layout.spec.ts` |
| Нагрузка | `scripts/load/collab-load.mjs`: N читателей (REST: страница, содержимое, поиск, дерево; пауза 0,5–1,5 с; у каждого живая реплика документа по WebSocket) + M редакторов (вставка помеченного фрагмента каждые ~1 с через протокол совместного редактирования). Задержки: подтверждение правки сервером (`collab.ack`), появление правки у каждого читателя (`collab.remote`), REST. В конце — каждая подтверждённая правка ровно один раз в копии сервера | `scripts/load/collab-load.mjs` |

Журнал всех прогонов: `test-results/perf/results.jsonl` (браузерные) и `test-results/load/*.json` (нагрузка); CI сохраняет `test-results/` как артефакт.

Запуск:

```bash
# браузерные замеры (собранный клиент, изолированный сервер)
npm run build -w @kb/web -- --outDir ../../.e2e-web --emptyOutDir
npx playwright test --project=desktop tests/e2e/perf-typing.spec.ts tests/e2e/perf-session.spec.ts
# профиль CPU и рендеры React во время набора (сборка без минификации: npm run build -w @kb/web -- --minify false --outDir ../../.e2e-web)
KB_PERF_PROFILE=1 KB_PERF_BLOCKS=5000 npx playwright test --project=desktop tests/e2e/perf-profile.spec.ts
KB_PERF_ENFORCE=1 npx playwright test --project=desktop tests/e2e/perf-typing.spec.ts   # на калиброванном стенде: бюджеты обязательны
KB_LONG_SESSION_MIN=20 npx playwright test --project=desktop tests/e2e/perf-session.spec.ts

# нагрузка (поднимает свой сервер на чистой БД; или --url https://kb.example.ru --email … --password …)
node --import tsx --conditions=development scripts/load/collab-load.mjs --readers 100 --editors 20 --pages 5 --blocks 200 --duration 120
```

### Найдено и исправлено при профилировании (CDP Profiler)

* Счётчик слов (`characterCount.words()`, обход всего документа) пересчитывался на **каждое** нажатие в `PageView` — теперь после паузы 600 мс.
* Индикатор «Сохранено» перерисовывался синхронно внутри транзакции редактора на каждый символ (подписка на счётчики, `Intl` форматтер создавался заново, подсказка с `floating-ui`) — теперь подписка только на отображаемое состояние, текст подсказки строится лишь при её открытии, форматтер даты один.
* Каждое сообщение присутствия (курсор соавтора) перерисовывало всю страницу — теперь только при реальном изменении списка.
* Селекторы плавающих панелей (`isActive` ×20, `can().splitCell()`) выполнялись на каждый символ, когда панели скрыты — теперь пропускаются.
* Итог при 1× на 700 блоках: p50 37 → 23–27 мс.
* 23.10 (D-34, `tests/e2e/perf-profile.spec.ts` с `KB_PERF_PROFILE=1` на неминифицированной сборке; в профиль добавлен подсчёт рендеров React через хук DevTools): ручка блока перерисовывала меню на каждое нажатие; индикатор сохранения и защита локальной копии рендерились на каждое изменение счётчиков, а каждый коммит React при фокусе в редакторе обходит текст всего документа (сохранение/восстановление выделения contenteditable) — индикатор теперь обновляет DOM напрямую; счётчик слов перерисовывал всю страницу — теперь только при открытой панели «Сведения»; ID блоков и подсветка кода обходили весь документ на каждый символ — теперь только изменённые места; prosemirror-view после пересборки документа привязкой Yjs глубоко сравнивал каждый блок на каждое нажатие — равные узлы подменяются текущими после обновления; привязка Yjs повторно синхронизировала уже синхронизированный документ на транзакциях без изменений — пропускается; оглавление сериализовало документ на каждое изменение — после паузы.

### Открытые дефекты производительности

1. **PERF-D1.** Ввод при CPU 4× не укладывается в бюджет: p95 ≈ 73 мс, p99 ≈ 104 мс (23.10, после D-34; было 96 / 120 мс в том же окне и 0,5–0,8 с под тяжёлой нагрузкой 22.10). Остаток — линейная работа y-prosemirror на каждое нажатие (`updateYFragment` по блокам верхнего уровня, относительные позиции курсора — для привязки и для курсора соавторов), отрисовка ProseMirror, запись журнала реплики в IndexedDB. Дальше — изменение библиотеки привязки (инкрементальная синхронизация изменённого диапазона) или виртуализация документа (§ «Типовая страница до 5 000 блоков: виртуализация»), замер на эталонном стенде.
2. **PERF-D2.** Документ 5 000 блоков: при 1× p50 ≈ 33 мс, p95 ≈ 62 мс, ячейка таблицы p95 ≈ 100–110 мс (23.10; до D-34 — p50 45–49, p95 74–86 в том же окне) — бюджет не выполнен. Вставка 5 000 блоков одной транзакцией в редакторе (`setContent`) по-прежнему квадратична (y-prosemirror `mapPositionMigration`); импорт на сервере этого не затрагивает.
3. **PERF-D3.** Главный экран: при загрузке списки заменяют скелетоны другой высоты, CLS ≈ 0,03 (страница документа: CLS ≈ 0,001).

## Soak (`scripts/load/soak.mjs`, QA26-25)

Скрипт держит небольшую постоянную нагрузку часами и следит за утечками и целостностью. Нагрузка:

* редакторы дописывают маркеры в свой абзац и удаляют старые, поэтому объём документа ограничен и рост памяти
  нельзя списать на содержимое;
* редакторы переподключаются и переоткрывают вкладку;
* читатели держат живые реплики (со сменой страниц) и делают REST-запросы;
* раз в минуту страница создаётся и удаляется в корзину.

Каждые 30 с снимаются RSS, куча V8, дескрипторы, задержка event loop, пул БД (`kb_db_pool_connections`) и сессии
БД (`pg_stat_activity`). Каждые 5 мин проверяется целостность: каждое подтверждённое добавление есть на сервере
ровно один раз, подтверждённое удаление не воскресло, реплики читателей получили все правки старше 15 с. В конце
считаются наклоны после прогрева и выносится вердикт (пороги — как у алертов утечек). Отчёт перезаписывается после
каждой проверки (`test-results/soak/soak-*.json`), поэтому прерванный прогон сохраняет данные.

```bash
# в среде разработки или на стенде: свой сервер на чистой БД
node --import tsx --conditions=development scripts/load/soak.mjs --duration 86400 --editors 6 --readers 10 --pages 3
# против установки: одна учётная запись, защищённые метрики, сессии БД через роль только на чтение
node --import tsx --conditions=development scripts/load/soak.mjs --url https://kb.example.corp --email … --password … \
  --metrics-token … --db-url postgres://ro@db/kb --duration 86400
```

Ночной прогон в CI — `.github/workflows/nightly-load.yml` (нагрузка 2 мин + soak 60 мин). В GitHub он ещё не
запускался.
