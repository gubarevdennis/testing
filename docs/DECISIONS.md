# Технические решения

Решения, не требующие бизнес-согласования, приняты самостоятельно по продуктовым принципам ТЗ (сохранность данных > удобство > скорость разработки). Формат: решение — причина — компромисс.

## D-01. Монолит Node.js + PostgreSQL, без отдельного брокера/кеша
**Причина.** ТЗ требует сохранности и простоты эксплуатации в корпоративной среде; PostgreSQL даёт транзакции, FTS, триггеры аудита, LISTEN/NOTIFY и очередь задач (`SKIP LOCKED`).
**Компромисс.** Горизонтальное масштабирование ограничено пропускной способностью одной БД; для текущего масштаба организации достаточно. Redis не используется (меньше компонентов для резервирования).

## D-02. CRDT (Yjs) + собственный протокол с подтверждением после фиксации
**Причина.** Требование «никогда не показывать "Сохранено" до записи на сервер» и работа офлайн. Стандартные провайдеры (y-websocket) не дают подтверждения на уровне операции.
**Компромисс.** Свой протокол нужно сопровождать; покрыт интеграционными, property-based и браузерными тестами.

## D-03. Заголовок страницы — `Y.Text` внутри документа
**Причина.** Одновременное переименование не должно терять ввод; заголовок синхронизируется в `pages.title` сервером.

## D-04. Поколение документа (`doc_state.generation`)
**Причина.** Восстановление из архива пересоздаёт CRDT-историю; старая локальная реплика в браузере иначе слилась бы с ней и задвоила текст. Реплика и очередь операций ключуются поколением.

## D-05. Редактор монтируется после загрузки реплики и первой синхронизации
**Причина.** Найдено браузерным тестом: редактор на пустом документе успевал записать служебные блоки в CRDT, после перезагрузки появлялись лишние пустые абзацы. Вместо «хвостового абзаца» (TrailingNode) — клик под последним блоком добавляет абзац; служебные нормализации выполняются только при праве редактирования (иначе читатель создавал бы неотправляемые изменения).

## D-06. Блоки с постоянными ID на сервере и клиенте
Нужны для ссылок на блок, комментариев, поиска «к совпадению», восстановления отдельного блока. Сервер присваивает ID при импорте/восстановлении, клиент — при локальных правках (только для локальных транзакций, чтобы не было «пинг-понга»).

## D-07. Markdown-маркеры `<!--kb:…-->`
Markdown-экспорт остаётся читаемым, а невыражаемая в Markdown семантика (выноски, колонки, объединённые ячейки, ширина изображений) восстанавливается при обратном импорте. Для буфера обмена маркеры отключаются.

## D-08. Хранилище файлов по SHA-256
Дедупликация, проверка целостности при бэкапе/восстановлении, неизменяемость объектов. Удаление — только сборщиком мусора после проверки ссылок и срока хранения.

## D-09. Тайлы deep-zoom для больших изображений
Просмотр схем склада в десятки мегапикселей без декодирования оригинала в браузере; оригинал всегда доступен для скачивания.

## D-10. Строже из противоречивых требований
* RTO: в ТЗ встречаются 2 ч и 60 мин — принято **60 мин**; RPO — **≤ 5 мин** (непрерывная архивация WAL), см. `BACKUP_RESTORE.md`.
* Задержка ввода: взято **≤ 50 мс** (p95), измеряется браузерным тестом (сейчас p95 ≈ 31 мс на 400 абзацах).
* Markdown-сокращения: по версии 2.0 ТЗ `> ␣` создаёт раскрывающийся блок, цитата — `" ␣`.
* Режим публикации по умолчанию — «живой» (`live`), согласование включается политикой пространства.

## D-11. 404 вместо 403 для недоступных страниц
Не раскрываем существование и названия. В хлебных крошках недоступные предки показываются как «скрыто».

## D-12. Аудит — append-only с хеш-цепочкой
Триггер запрещает UPDATE/DELETE; канонический JSON для стабильного хеша; проверка `npm run audit-verify` и в админке.

## D-13. Санитизация HTML на сервере через sanitize-html (вместо DOMPurify)
DOMPurify в серверном DOM (happy-dom) вырезал заголовки; sanitize-html работает без DOM, тот же allowlist используется для SVG.

## D-14. Собственная реализация TOTP (RFC 6238)
Библиотека otplib v13 сменила API; RFC реализован в 40 строк и покрыт тестом с эталонными векторами.

## D-15. Сервер отдаёт собранный клиент сам (WEB_DIST), с `wildcard: true`
Новая сборка подхватывается без перезапуска; запросы к `/assets/*` без файла отвечают 404, а не index.html (иначе старые вкладки после обновления получали HTML вместо JS).

## D-16. Стабильные пропсы меню Tiptap
Найдено браузерным тестом: нестабильные объекты опций у `BubbleMenu`/`DragHandle` перерегистрировали плагины на каждой отрисовке, что пересоздавало привязку Yjs и полностью перерисовывало документ (терялась отметка формата у курсора, лишняя нагрузка). Опции вынесены в константы, состояние форматирования читается через `useEditorState`.

## D-17. Ленивые тяжёлые модули клиента
Конвертер Markdown (remark+YAML) и Mermaid грузятся по требованию; стартовый бандл ≈140 КБ gzip. KaTeX остаётся в чанке редактора (подключается расширением Tiptap статически).

## D-18. Только Chromium в автоматических браузерных тестах
В окружении нет Firefox/WebKit и реальных устройств; это зафиксировано как ограничение в `RELEASE_READINESS.md`, проверки в других браузерах — ручной чек-лист.

## D-19. Доступный контраст при сохранении токенов ТЗ
Белый текст на `#5A85C6` даёт 3,75:1 (ниже WCAG AA 4,5:1). Акцентный цвет ТЗ сохранён для фокуса, ссылок и выделения, а фон основной кнопки — `--accent-strong` `#3F6AAB` (5,4:1). Границы полей ввода — отдельный токен `--border-input` (3,3:1), декоративные границы остаются `#E5E8ED`. Цвета статусов, бейджей, аватаров затемнены до ≥ 4,5:1; проверяется axe в E2E.

## D-20. Копия конфликта «правка ↔ удаление» определяется на клиенте
CRDT при слиянии отбрасывает правки внутри удалённого блока, и сервер не может надёжно восстановить их из журнала (сборка мусора Yjs). Клиент же знает, какие блоки правил его пользователь: если удалённое изменение удаляет блок, правленный за последние 10 минут, версия пользователя сохраняется на сервере (`/api/v1/pages/:id/conflicts`) и предлагается вернуть её одной кнопкой. Работает в обоих порядках событий и после работы офлайн. Ограничение: перемещение блока, при котором правки другого автора не вошли в новую копию, пока не распознаётся.

## D-21. Пустая страница, созданная «+», уходит в корзину при уходе автора
Только если у неё нет заголовка, текста, файлов, комментариев, дочерних страниц и правок других людей, и она создана тем же пользователем менее суток назад. Страница не удаляется безвозвратно (корзина), чтобы исключить потерю данных при ошибке проверки.

## D-22. Локальные данные браузера привязаны к пользователю
Реплики документов, очередь неотправленных изменений и кеш метаданных ключуются `userId`: на общем компьютере изменения одного сотрудника не могут уйти от имени другого. При выходе с неотправленными изменениями показывается предупреждение.

## D-23. Статус «Сохранено на устройстве» — только после записи в IndexedDB
Операция удаляется из локальной очереди только после завершения своей записи; ошибка записи (переполнение, приватный режим) переводит индикатор в ошибку с понятным текстом, а не в «сохранено».

## D-24. Минимальные привилегии в модели доступа (сводка решений)
* Роль администратора/владельца организации управляет системой, а не содержимым: она не открывает личные и закрытые материалы. Экстренный доступ — только для чтения (без экспорта, скачивания и шаринга), на 1–72 ч, с основанием, утверждением **вторым** администратором, уведомлением владельца материала и записью каждого шага в аудит (`/api/v1/admin/emergency-access`).
* Аудитор читает журнал, но названия документов без доступа маскируются; «Проверить доступ» и матрица прав считают решение на сервере по тем же правилам, без входа под чужой учётной записью; личные пространства в матрице не показываются.
* Нельзя выдать уровень выше собственного; гостю — не выше «Редактирования»; гости не входят в «всю организацию». Расширение аудитории (вся организация, перенос в общую область, «Вся компания») требует подтверждения с именами получателей; «Только я» показывает, кто потеряет доступ.
* Публичные ссылки выключены политикой организации по умолчанию; при выключении политики все ссылки перестают работать; ссылка живёт, только пока её автор сам вправе делиться страницей; `noindex` по умолчанию; скачивание — отдельный флаг. Префикс `/pub/` (не `/s/` — это маршрут пространства в клиенте).
* При увольнении частные заметки никому не передаются: преемник получает только документы, которыми сотрудник уже делился; аудит содержит только количества.
* Кеш эффективных прав **не используется**: права считаются одним запросом к PostgreSQL на каждый запрос (D-01), `acl_epoch` служит для перепроверки открытых WebSocket-сессий. Кеш, ключуемый эпохой, был бы корректен только при поднятии эпохи на любом изменении (включая прямые изменения в БД и истечение сроков), а выигрыша по числу запросов он не даёт.
* UI никогда не решает сам: кнопки и формы строятся по `actions`, которые вернул сервер, и сервер повторно проверяет каждое действие (проверено браузерными тестами `tests/e2e/acl-p0-ui.spec.ts`).


## D-25. Редактор: курсор при чужих правках, починка таблиц, загрузки как блоки
* **Курсор.** `@tiptap/y-tiptap` 3.0.x «восстанавливает» позицию курсора, если текст его абзаца изменился в удалённом обновлении, и оставляет прежнее смещение — курсор прыгал, когда соавтор печатал перед ним (найдено `tests/e2e/editor-p0-core.spec.ts`). Расширение `apps/web/src/editor/extensions/stableSelection.ts` заново разрешает относительные позиции Yjs, снятые до удалённой транзакции; библиотеке оставлен только случай удалённого текстового узла.
* **Таблицы после конкурентных правок.** Строка и столбец, добавленные одновременно, дают «рваную» таблицу. Починка prosemirror-tables к удалённым изменениям в Yjs не записывалась (у каждого — своя), а запись всеми удвоила бы ячейки. Решение (`extensions/tableRepair.ts`): починка, добавленная к удалённому изменению, подавляется; её записывает один редактор — с наименьшим clientID Yjs среди присутствующих редакторов (поле `kbCanEdit` в awareness). Компромисс: при рассинхронизации присутствия двое могут починить одновременно — тогда появится лишний пустой столбец, но данные не теряются.
* **Загрузки.** Вставленный/перетащенный файл сразу становится блоком документа с `uploadId` (не декорацией); файл хранится в IndexedDB `kb-uploads` до подтверждения сервера и после перезагрузки дозагружается; завершение — изменение атрибутов без шага Undo. Индикатор показывает «Загрузка файлов…», пока файл не на сервере.
* **Изображение по ссылке** копируется сервером (`POST /api/v1/attachments/from-url`) через SSRF-защищённый `remote-fetch` и проверку содержимого, а не встраивается внешней ссылкой: страница не зависит от внешнего сайта и не раскрывает ему читателей.

## D-26. Версии хранят свойства страницы; восстановление — всегда новая версия с точным предпросмотром
* Каждая ревизия хранит снимок свойств (`page_revisions.props`: значок, обложка, статус, владелец, теги, поля, защита, ширина, дата пересмотра) и версию схемы содержимого. Сравнение версий показывает и текст (блоки + слова), и свойства; у ревизий, созданных до этого, честно написано «свойства не сохранялись».
* Восстановление статьи или одного блока: сначала текущее состояние сохраняется как «pre-restore», затем изменение идёт через CRDT, результат — новая ревизия `restore`. Более поздние версии и журнал аудита не трогаются (только дописываются). Свойства возвращаются только по явному выбору; статус и защита — состояние процесса и не откатываются; права доступа не откатываются никогда (ACL-173).
* `dryRun` у восстановления возвращает точные последствия (что изменится в тексте, какие свойства вернутся и какие нет, номера будущих версий, сколько поздних версий останется, кто сейчас редактирует) — UI показывает это вместо общего «Вы уверены?».
* Изменения свойств через API журналируются с `before` и `after`; отмена (`POST /pages/:id/events/:eid/undo`) применяется только к полям, которые с тех пор никто не менял (иначе 409 со списком полей), и сама отменяема.
* Отпечаток блока для сравнения считается по JSON с упорядоченными ключами: jsonb меняет порядок ключей, и без этого неизменённые блоки ревизии выглядели «изменёнными».

## D-27. Неслиемый конфликт — диалог из трёх вариантов, а не всплывающее уведомление
* Блочный конфликт (правка ↔ удаление/перенос, D-20) открывает диалог сравнения «Ваша версия / Сейчас в документе» с вариантами «Оставить мою», «Сохранить обе» (моя версия вставляется отдельным блоком с новыми id), «Принять версию сервера» (копия остаётся в истории страницы). «Решить позже» оставляет видимое напоминание до решения — конфликт не скрывается.
* Отказ сервера в изменениях документа (`invalid_update`, `too_large`, `deleted`, `schema_outdated`) открывает тот же диалог для всего документа: «Сохранить обе» создаёт рядом новую страницу с локальной версией (`POST /pages/:id/conflict-copy`: JSON, если он проходит серверную проверку после очистки и миграции, иначе Markdown), «Принять версию сервера» — после явного подтверждения удаляет неотправленные операции и локальную реплику (`CollabProvider.discardUnsynced`) и открывает документ заново, «Сохранить локальную копию» — файл.

## D-28. Миграция схемы документа на живых документах
* Документ мигрирует при первом открытии сервером новой версии (или явным `hub.migrateSchema`): версия «перед миграцией», применение миграции через CRDT, `pages.content_schema_version`, ревизия `migration`, событие и аудит. Цепочка миграций проверяется до изменений; при разрыве документ открывается только для чтения и не меняется.
* Клиент сообщает версию схемы своего редактора в HELLO. Редактор старой схемы не получает мигрированный документ (иначе его неотправленные правки внутри перестроенных блоков пропали бы и локально): соединение закрывается с `schema_outdated`, локальная версия сохраняется и предлагается диалогом D-27. Клиент новее сервера (поэтапное обновление) получает `schema_newer`: операции остаются в очереди и отправляются после обновления сервера — ничего не теряется и не смешивается.
* Восстановление версии или состояния журнала, сохранённого до миграции, сначала мигрирует содержимое до текущей схемы.

## D-29. Теги, slug и источники поиска
* Теги — массив `pages.tags` (нормализация: без «#», пробелы схлопнуты, уникальны без учёта регистра). Slug вычисляется триггером из названия (транслитерация) и косметичен: идентичность ссылки — UUID, `/p/<id>/<slug>` и `/p/<id>` открывают одну страницу, переименование и перенос ссылок не ломают.
* Индекс поиска хранит теги и заголовки разделов отдельно (вес A), результат сообщает источник совпадения («в тегах», «в заголовке раздела»); фильтр `tag=`. Права применяются до подсчёта, как и для остальных источников.

## D-30. Тяжёлые операции не блокируют ввод
* Контрольная сумма больших загрузок (поточный SHA-256) считается в Web Worker; при сбое воркера файл перехэшируется по частям с уступкой главного потока. Измерено (CPU ×4, файл 48 МБ, экспорт параллельно): на главном потоке p99 задержки ввода 605 мс и 11 задач > 100 мс; с воркером p99 92 мс, 0 задач > 100 мс (`tests/e2e/perf-background.spec.ts`, журнал `test-results/perf/results.jsonl`). Экспорт и OCR выполняются фоновыми заданиями на сервере.
* Импорт в коллекцию в режиме «Заменить» приводит коллекцию к файлу: обновление по ключу, добавление новых строк, строки, которых нет в файле, — в корзину (восстановимо). Пробный прогон показывает, что будет удалено; без явного подтверждения сервер отказывает. Повтор ключа в файле обновляет одну запись — скрытых дублей нет (раньше режим «обновить по ключу» создавал дубль).

## D-31. Перетаскивание блоков — собственная логика указателя, модель отдельно от отображения
* Встроенный drag-and-drop браузера (Tiptap `DragHandle` + `Dropcursor`) не позволял задать порог, цель «внутрь», подсветку контейнера, объяснение недопустимой цели, управляемую автопрокрутку, копирование и перенос на другую страницу. `DragHandle` теперь только позиционирует ⋮⋮ (в том числе у блоков внутри колонок — правило `nested`), а перетаскивание ведёт `apps/web/src/editor/menus/blockDrag.ts` (pointer events, порог 5 px, превью с прозрачностью, линия до/после/внутрь, рамка колонки/контейнера, красная линия и причина для недопустимой цели, автопрокрутка у краёв, Alt/Ctrl — копия, Esc — отмена, отпускание над страницей в дереве — перенос туда).
* Модель — `apps/web/src/editor/blockDrop.ts` (покрыта юнит-тестами): единица переноса — блок, родитель которого контейнер (страница, колонка, выноска, цитата, тело раскрывающегося блока); списки, таблицы, изображения и наборы колонок переносятся целиком. Недопустимо: внутрь самого себя, набор колонок в колонку, всё, что запрещает схема. Отпускание — одна транзакция и отдельный шаг Undo; блоки сохраняют id и порядок, копия получает новые id; контейнер, из которого ушёл последний блок, получает пустой абзац (колонка не может быть пустой).
* Перенос на другую страницу — тем же путём, что «Переместить на страницу…» (`moveToPage.ts`): сначала блоки записываются на целевую страницу и подтверждаются сервером, только потом удаляются здесь — сбой сети или отказ прав оставляет копию, а не теряет блок.
* Клавиатурные аналоги: Alt+Shift+↑/↓ (на первом/последнем блоке контейнера — вынос из контейнера), Esc на выделенном блоке внутри колонки/выноски выделяет весь контейнер, меню блока «Переместить на страницу…». На сенсорных экранах ручки нет (нет наведения): плавающая кнопка «Действия с блоком» рядом с «+» открывает то же меню для блока под курсором (вверх/вниз, на другую страницу, дублировать, превратить, удалить) — вариант «доступное меню «Переместить»» из ТЗ; перетаскивание долгим нажатием не реализовано. Выделенное изображение меняет ширину с клавиатуры: Alt+Shift+←/→ (±10 % ширины текста).
* Дерево страниц: цель «перед/после» страницы теперь тоже недопустима (явно, до отпускания), если у пользователя нет права создавать страницы у её родителя или в её пространстве — раньше такая цель выглядела допустимой и отказ приходил от сервера уже после отпускания.

## D-32. Буфер обмена: внутренний формат, RTF, вложения при переносе между страницами
* Копирование и вырезание пишут `text/html` (переносимая разметка), `text/plain` (TSV для диапазона таблицы) и `application/x-kb-blocks+json` — JSON фрагмента с типами узлов, id блоков и всеми атрибутами (ширины колонок, размер и выравнивание изображения, иконка выноски), которые HTML не переносит. Во внутренний формат не попадают якоря комментариев исходной страницы и названия страниц, недоступных читателю (AT-79). Вставка: внутренний формат → HTML → текст. Данные этого типа считаются недоверенными (их может положить любой сайт): принимаются только с того же origin, собираются через схему, URL очищаются `sanitizeDocUrls`.
* Изображения и файлы, вставленные или перенесённые на другую страницу, копируются сервером в вложения этой страницы (`POST /api/v1/attachments/:id/copy`, общий blob по SHA-256, аудит `attachment.copy`): читатели целевой страницы их видят, права — целевой страницы. Требуется право скачивания на исходной странице и редактирования на целевой (как при дублировании страницы); без права скачивания остаётся ссылка на исходное вложение, пользователь предупреждается.
* RTF разбирается собственным модулем (`clipboard/rtf.ts`, только нужное: абзацы, H1–H6 по уровню структуры/стилю, списки по уровням, таблицы, ссылки, PNG/JPEG). Буфер только с RTF становится HTML; у Word картинки в HTML — локальные файлы, недоступные браузеру, поэтому они берутся из RTF той же копии (если число совпадает — иначе порядок был бы догадкой). Встроенные картинки остаются на своём месте вместе с подписью и загружаются прямо в эти блоки; картинки с других сайтов (Google Docs, веб, почта) копируются на сервер через `from-url` (D-25), при неудаче остаются внешними ссылками с предупреждением.
* Нормализация входящего HTML дополнена: вложенные списки Google Docs (список внутри списка, `aria-level`), заголовок/цитата/подпись рисунка Word, обёртки перенаправлений Google, навигация и формы веб-страниц, разрывы строк между блоками.

## D-33. Шаги Undo — по операциям пользователя
* Менеджер отмены Yjs объединяет все изменения за 500 мс: форматирование сразу после набора, перенос блока, изменение размера изображения или столбца, преобразование блока отменялись вместе с набором вокруг. `extensions/historyBoundaries.ts`: набор текста (ввод, удаление, Enter/Backspace между абзацами) по-прежнему группируется, любое другое локальное изменение — отдельный шаг (захват останавливается до записи изменения в Yjs и после неё).
* Ctrl/Cmd+Z, Ctrl/Cmd+Shift+Z, Ctrl+Y при фокусе на кнопке внутри блока (панель изображения) выполняют отмену редактора: встроенная отмена браузера над редактируемым DOM удаляла блок целиком. Кнопки панели изображения не забирают фокус у документа.

## D-34. Задержка ввода: устранённые причины (PERF-D1/D2)
* Найдено профилированием CDP (`tests/e2e/perf-profile.spec.ts`, `KB_PERF_PROFILE=1`, неминифицированная сборка; хук React DevTools считает, какие компоненты рендерились при наборе): (1) ручка блока перерисовывала меню на каждое нажатие (плагин сообщает `node: null` на keydown); (2) индикатор «Сохранено/Сохранение…» и защита локальной копии рендерились на каждое изменение счётчиков — а каждый коммит React при фокусе в contenteditable сохраняет и восстанавливает выделение, обходя текст всего документа; (3) счётчик слов перерисовывал всю страницу каждые 600 мс; (4) ID блоков обходили весь документ на каждый символ; (5) подсветка кода (lowlight) обходила документ дважды на каждую транзакцию; (6) prosemirror-view сравнивал каждый блок глубоко (`Node.eq`), потому что после пересборки документа привязкой Yjs описания блоков хранили равные, но не те же узлы; (7) привязка Yjs заново синхронизировала уже синхронизированный документ на каждой транзакции без изменений документа; (8) оглавление сериализовало документ на каждое изменение.
* Исправления: перерисовка только при смене типа блока; индикатор обновляет DOM напрямую, защита подписана на производное значение; счётчик слов — только при открытой панели; проверка ID пропускается для изменений внутри одного текстового блока; инкрементальная подсветка с кэшем по узлу; после обновления вида равные узлы подменяются текущими (`extensions/editorPerf.ts`); повторная синхронизация того же документа пропускается (обёртка метода привязки, проверено тем, что план миграции позиций никогда не относится к уже синхронизированному документу); оглавление — после паузы. Остаток — линейная работа y-prosemirror (`updateYFragment`, перевод позиций курсора в относительные) и запись журнала в IndexedDB; без изменения библиотеки или виртуализации документа он не устраняется.

## D-35. Согласовано заказчиком (23.10.2026)
* **Кеш эффективных прав не используется** (R-ACL-026, R-ACL-046): права вычисляются одним запросом к PostgreSQL на каждое обращение, `acl_epoch` используется для перепроверки открытых WebSocket-сессий. Отзыв прав действует немедленно, устаревшего кеша не существует.
* **Отдельный уровень Workspace не вводится** (R-TREE-005): организация и есть рабочее пространство; иерархия Organization → Space → Page.
* Прочие решения, не требующие бизнес-согласования, принимаются командой по продуктовым принципам ТЗ (сохранность данных > предсказуемость > скорость) и фиксируются здесь.

## D-36. Сноски — узел в тексте, который несёт текст примечания; схема документа 2
* **Модель.** Сноска (R-EDITOR-038) — встроенный атомарный узел `footnote` с содержимым `(text | hardBreak)*`: текст примечания хранится в самой ссылке. Номер — порядок ссылок в документе (CSS-счётчик в редакторе, вычисляется экспортёрами), нигде не хранится. Поэтому вставка, удаление, перенос, копирование и одновременная правка не могут рассинхронизировать номера и примечания; копирование/вырезание/перенос на другую страницу/дублирование переносят примечание вместе со ссылкой; удаление ссылки и её примечания — один шаг Undo. Альтернатива «ссылка в тексте + отдельный список примечаний в конце» отвергнута: два места, которые нужно согласовывать при каждой правке и при слиянии CRDT, и примечания, теряющиеся при копировании фрагмента.
* **Редактирование.** Выбор ссылки (щелчок, стрелки, Ctrl+Alt+F, «/Сноска», «Ещё» → «Сноска») открывает всплывающее окно с маленьким редактором ProseMirror, привязанным к содержимому узла (классическая схема ProseMirror footnote): каждое нажатие — шаг транзакции страницы, поэтому совместная правка посимвольная (Yjs), Ctrl+Z/Ctrl+Shift+Z внутри окна — отмена страницы, набор в примечании группируется как набор текста (D-33). Esc/Ctrl+Enter возвращают курсор за ссылку. Под статьёй — список «Сноски» (пересчёт после паузы, D-34) с переходом «↑» к ссылке; из окна — «↓ К списку сносок».
* **Форматы.** Markdown — `[^n]` и `[^n]: текст` (определения без ссылок не теряются: абзацы в конце и предупреждение; одна сноска с несколькими ссылками повторяется у каждой). HTML/PDF/публичная ссылка/предпросмотр — надстрочная ссылка `#kb-fn-N` и список `<section class="kb-footnotes">` с обратными ссылками; DOCX — настоящие сноски Word (`footnotes.xml`). Импорт распознаёт сноски Word (DOCX через mammoth и HTML буфера), Google Docs, GitHub/pandoc и собственный экспорт: ссылка на цель внутри документа считается сноской, только если цель — в известном списке сносок или ссылается обратно (обычные якоря `#раздел` не трогаются). Концевые сноски Word становятся обычными (с предупреждением). Поиск и сравнение версий видят текст примечания в абзаце (` [текст]`).
* **Миграция схемы 1 → 2** (D-28): `CONTENT_SCHEMA_VERSION = 2` (`packages/shared/src/editor/version.ts`, без зависимостей — его объявляет и клиент совместной работы в HELLO по умолчанию). Новые узлы документ версии 1 не ломают; миграция дополнительно превращает в настоящие сноски прежнее представление импортёров версии 1 (надстрочные «[n]» + раздел «Сноски» с нумерованным списком в конце) — только если структура однозначна (ровно один такой раздел с нумерацией с 1, каждая цифра использована, других надстрочных «[n]» нет, после раздела только служебные блоки); иначе документ не меняется. Новые страницы, восстановление архива и частичное восстановление записывают `pages.content_schema_version` и версию первой ревизии текущими — иначе первая же загрузка «мигрировала» бы уже новое содержимое. Тест `tests/integration/collab-schema.test.ts` построен относительно поставляемой версии (BASE → BASE+1 поверх реестра) и проверяет реальную миграцию 1 → 2 с клиентом формата 1.

## D-37. Изображения в строке
* Отдельный узел `inlineImage` (встроенный, атомарный) рядом с блочным `image`: та же модель вложения (оригинал — вложение страницы, `src` — адрес содержимого, миниатюры только производные), размер в px, вертикальное выравнивание в строке (`valign`: базовая линия/центр/верх/низ), alt, подпись (`title`: подсказка и подпись в просмотрщике), просмотрщик, «Скачать оригинал», Alt+Shift+←/→ (±25 %), перетаскивание маркера. «Сделать блоком» / «В строку текста» — одна транзакция (один шаг Undo), вложение то же.
* **Строка или блок.** `<img>` с текстом или другими картинками в том же абзаце/заголовке/ячейке — в строке; одна картинка в абзаце или в `<figure>` — блок (без пустого абзаца перед ним: такой абзац заменяется картинкой при нормализации). Markdown: то же правило; собственный маркер `<!--kb:{"t":"image","inline":true}-->` фиксирует выбор при обмене. Файлы, вставленные или перетащенные отдельно, — блоки (предсказуемо); в строку их переводит кнопка.

## D-38. Один конвейер для импорта и буфера обмена
* Всё, что входит в документ, проходит `packages/shared/src/editor/ingest.ts` + `html-normalize.ts`: HTML (буфер, файлы .html, DOCX после mammoth, HTML-блоки Markdown), Markdown (файлы, ZIP, `text/markdown`, похожий на Markdown текст), простой текст (абзац на строку — одинаково для .txt и вставки), строки таблиц (CSV/XLSX «как таблица» и диапазон TSV), файлы и изображения (узлы загрузки). В браузере код работает на DOM страницы (`DOMParser`), на сервере — на happy-dom (`convert/html.ts withHtmlParser`); порядок предпочтения форматов буфера (`clipboardKind`) тоже общий. Нормализация — бывшая клиентская (Word-списки, Google Docs, сноски, палитра, трекеры), разбор — правила схемы ProseMirror, завершение (`finalizeIngest`) — безопасность URL, id блоков, проверка схемы, отчёт `{converted, dropped, warnings}` с одинаковыми формулировками. Браузер сам делает только то, что требует сети и редактора: загрузка встроенных картинок в их блоки, копирование вложений других страниц, передача картинок других сайтов в обработчик `clipboard/hooks.ts` (по умолчанию — серверное копирование `from-url`), вставка одним шагом Undo (`Slice.maxOpen`, как у ProseMirror); вставка диапазона в существующую таблицу по-прежнему идёт ячейками (prosemirror-tables) из того же нормализованного HTML.
* Серверный sanitize-html больше не участвует в импорте: граница безопасности импорта — общий allowlist-нормализатор + построение узлов только по схеме + `sanitizeDocUrls`/`finalizeIngest`; sanitize-html оставлен для HTML, который хранится или отдаётся как HTML. Иначе одинаковое содержимое давало разные документы (разные списки атрибутов и стилей).
* Сознательные различия: первая H1 файла становится названием страницы, а во вставке остаётся заголовком; картинки других сайтов при импорте копирует сервер в пакет импорта, при вставке — обработчик после вставки. Тесты доказывают совпадение документа и отчёта: `tests/unit/editor-footnotes-ingest.test.ts` (HTML/MD/текст/TSV/встроенные картинки), `tests/integration/media-ingest-p0.test.ts` (эндпоинт импорта против вставки), `tests/e2e/editor-footnotes-media.spec.ts` (вставка в браузере против импорта файла).

## D-39. Картинка, попавшая на другую страницу, становится вложением этой страницы — на всех путях
* Одно правило и один модуль (`apps/server/src/services/attachment-copy.ts`): копия — новое вложение целевой страницы с тем же blob (без повторной загрузки, оригинал байт-в-байт), аудит `attachment.copy`; условие — право скачивания там, где файл сейчас; иначе ссылка остаётся (читатели цели её не увидят) и пользователь предупреждается (D-32). Пути: вставка между страницами — внутренний формат и теперь также HTML без него (`data-attachment-id`), перенос и перетаскивание блоков на страницу (`moveToPage.ts`), дублирование страницы (кроме своих файлов — и картинки, на которые содержимое ссылается с других страниц), страница из шаблона, копия при конфликте («Сохранить обе»).
* **Шаблоны.** При сохранении шаблона (из страницы или JSON, при обновлении из страницы) файлы содержимого копируются в активы шаблона (без страницы, автор шаблона — у него было право скачивания); страница из шаблона копирует их себе для любого пользователя шаблона — шаблон перестаёт зависеть от исходной страницы (корзина, права). Чужой файл в JSON-шаблоне, который автор не может скачать, не копируется — шаблон не становится способом вынести файл.

## D-40. Безопасность интеграций (SEC-L1, SEC-L3, SEC-L4, R-ACL-036), 23.10.2026
* **Картинки других сайтов не показываются напрямую.** CSP `img-src 'self' data: blob:`; вставленные картинки копирует сервер (`from-url`, SSRF-защита). Цена: картинки, вставленные ссылками раньше, перестают отображаться — их нужно добавить заново. Альтернатива «прокси-просмотр через сервер без сохранения» отвергнута: тот же исходящий запрос на каждый просмотр и зависимость документа от чужого сайта.
* **Антивирус fail closed.** Без вердикта clamd (недоступен, тайм-аут, ошибка, лимит размера) файл не принимается; пользователю — понятная причина (503/413), эксплуатации — метрика и алерт. Доступность загрузки уступает защите.
* **SSO.** Учётная запись связывается с `sub` IdP при первом входе; e-mail, уже связанный с другим `sub`, отклоняется (переиспользованный адрес). Группы и отдел из claims сопоставляются по имени с существующими группами, не создаются; снимаются только членства, добавленные SSO. Недоступный IdP не мешает запуску и входу по паролю.
* **Общие лимиты — только там, где они защищают** (вход, пароли публичных ссылок, начало загрузок): счётчик в PostgreSQL с локальным быстрым путём для превысивших ключей; общий лимит API от перегрузки остаётся на экземпляр (без запроса к БД на каждый запрос). Отдельный Redis не вводится.
* **«Участники пространства X» как получатель доступа** — участники на момент проверки (активное разрешение на X пользователю, его группе/отделу или всей организации, без запрета), на один уровень: разрешение «участникам Z», где Z сам открыт «участникам X», участников X к Z не добавляет (без циклов и неожиданных цепочек). Членство пересчитывается на каждом запросе (без кеша, D-35), поэтому вход в X и выход из него действуют сразу.
