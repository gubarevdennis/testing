# Резервное копирование и восстановление

Документ описывает фактически реализованную и испытанную схему: скрипты `scripts/backup/*`, автоматические
тесты `tests/resilience/backup-restore.test.ts` и протокол замеров от 22.10.2026. Эксплуатационные процедуры — в
[`OPERATIONS.md`](OPERATIONS.md), детали WAL/PITR — в [`scripts/backup/wal-archive.md`](../scripts/backup/wal-archive.md).

## 1. Цели (RPO/RTO) и их соответствие ТЗ

В ТЗ цели заданы в нескольких местах с разными значениями. Проектируем по самым строгим:

| Источник в SPECIFICATION.md | RPO | RTO | Сценарий |
|---|---|---|---|
| §«Нефункциональные» (стр. 84), §1316 «Восстановление после аварии», R-BACKUP-001 | ≤ 5 мин | ≤ 2 ч | катастрофический отказ |
| §13 (стр. 339), R-BACKUP-004 | ≤ 15 мин | ≤ 4 ч | согласованный типовой инцидент |
| стр. 564 | ≤ 5 мин | ≤ 2 ч | бэкапы БД, объектов, метаданных |
| стр. 657 | ≤ 5 мин | **≤ 60 мин** | «цели для проектирования» |
| стр. 952 | ≤ 5 мин для подтверждённых сервером изменений | ≤ 2 ч для всей организации | проектные цели |

Принятые цели: **RPO ≤ 5 мин**, **RTO ≤ 60 мин** (проектная), с запасом до 2 ч (обязательная для катастрофы).
Под RPO понимаются *подтверждённые сервером* изменения: клиент показывает «Сохранено» только после COMMIT в
`doc_updates` (E-13). Неподтверждённые изменения остаются в локальной очереди клиента и досылаются после
восстановления (это проверяют тесты сбоев, раздел 7).

### Как схема обеспечивает цели

| Механизм | Что покрывает | Вклад в RPO | Расписание |
|---|---|---|---|
| Непрерывное архивирование WAL (`archive_timeout=60s`, `wal-archive.sh`) + базовые копии `pg_basebackup` | вся БД: документы (журнал CRDT), версии, права, аудит | **≈ 1 мин** | непрерывно; базовая копия ежедневно или еженедельно |
| `backup.sh --objects-only` | новые файлы (вложения, производные) в пул копий | **≤ 5 мин** | каждые 5 мин (cron) |
| `backup.sh` (полная логическая копия) | согласованный снимок БД (`pg_dump` в экспортированном снимке) + список объектов + манифест | 24 ч сама по себе | ежедневно 02:15 |
| `verify-backup.sh` | доказательство восстановимости | — | еженедельно, плюс перед каждым релизом |
| Внутренний архив организации (`services/archive.ts`) | логический экспорт для переноса/чтения без приложения | **не DR-механизм** | по требованию |

Без WAL-архивации и частой синхронизации объектов RPO = 24 ч, и требование не выполняется. Это обязательная часть
промышленной установки (`deploy/docker-compose.yml` включает `archive_mode=on`).

## 2. Что входит в резервную копию

```
BACKUP_DIR/
  objects/<aa>/<sha256>[.enc]     общий пул объектов (контентная адресация, инкрементально, дедупликация)
  objects/index.log               «sha256 размер ключ» для всех сохранённых объектов (для PITR)
  kb-20261022T021500Z/
    db.dump[.enc]                 pg_dump -Fc --no-owner, снят в экспортированном снимке REPEATABLE READ
    objects.list                  «sha256 размер ключ» каждого объекта хранилища на момент копии
    manifest.json                 формат kb-backup/1: время, длительности, размеры, sha256, версия схемы,
                                  число строк 24 ключевых таблиц (тот же снимок, что и дамп)
    SHA256SUMS                    контрольные суммы файлов каталога (sha256sum -c)
    base/                         опционально: физическая копия для PITR (BACKUP_PG_BASEBACKUP=1)
```

* **Согласованность.** Сначала снимается дамп, затем копируются объекты. Объекты неизменяемы и адресуются по
  sha256, поэтому все блобы, на которые ссылается дамп, к моменту копирования уже существуют. Счётчики строк
  в манифесте снимаются в том же снимке, что и дамп (`pg_export_snapshot` + `pg_dump --snapshot`).
* **Инкрементальность.** Объект копируется в пул один раз. Повторная копия без новых файлов заняла 0,1 с
  на 500 объектах / 524 МБ.
* **Целостность.** Каждый новый объект хешируется при копировании. Если содержимое блоба не совпадает с его
  адресом, копия **прерывается** (сообщение `INTEGRITY:`), чтобы не сохранить повреждённые данные молча.
* **Шифрование.** Задаётся переменной `BACKUP_ENCRYPT_CMD`: это фильтр stdin→stdout, например `age -R pub`,
  `gpg -e -r …` или `openssl enc -aes-256-cbc -pbkdf2 -pass env:…`. Шифруются дамп и каждый объект пула.
  Манифест хранит sha256 и шифротекста, и открытого текста. Ключи в скриптах не хранятся. Ключ расшифрования
  (`BACKUP_DECRYPT_CMD`) нужен только там, где выполняется восстановление.
* **Учёт.** Каждый запуск пишется в таблицу `backups` (status, размер, checksum, `verified_at`). Это даёт
  метрики `kb_backup_age_seconds` и `kb_restore_verification_age_seconds`, а также предупреждения в панели
  «Здоровье системы». Независимо от приложения пишется textfile-метрика `kb_backup_last_success_timestamp_seconds`
  для node_exporter.
* **Хранение.** Как в ТЗ: ежедневные копии 30 дней, еженедельные 12 недель, ежемесячные 12 месяцев
  (`BACKUP_KEEP_DAILY/WEEKLY/MONTHLY`). Дополнительно всегда хранятся 3 последние копии (`BACKUP_KEEP_LAST`).
  Сборщик мусора удаляет из пула только объекты, на которые не ссылается ни одна оставшаяся копия и которые
  старше самой старой из них.

## 3. Расписание (промышленная установка)

| Что | Когда | Команда |
|---|---|---|
| WAL | непрерывно | `archive_command = '… wal-archive.sh %p %f'`, `archive_timeout = 60s` |
| Синхронизация объектов | `*/5 * * * *` | `backup.sh --objects-only` |
| Полная копия | ежедневно 02:15 (`deploy/systemd/kb-backup.timer` или сайдкар `backup` в compose) | `backup.sh` |
| Базовая копия для PITR | ежедневно или еженедельно | `BACKUP_PG_BASEBACKUP=1 backup.sh` или `pg_basebackup` |
| Проверка восстановления | еженедельно (воскресенье) + перед релизом | `verify-backup.sh --latest /backups` |
| Восстановление отдельных страниц/вложений | ежемесячно (ТЗ, стр. 956) | `restore.sh` во временную БД, затем `cli restore-pages` (раздел 4.1) |
| Полное учение по восстановлению организации | ежеквартально, с протоколом времени | раздел 5, «Восстановление после аварии» |
| Копия вне основного контура | каждые 5 мин | сервис `offsite` в compose (`--profile offsite`): `aws s3 sync` копий и архива WAL в бакет с Object Lock в режиме COMPLIANCE (правило 3-2-1, ТЗ стр. 954). Ключ без права удаления, бакет настраивает администратор хранилища (команды — в комментарии к сервису). |

Копирование выполняется отдельной ролью оператора резервного копирования (ТЗ стр. 958). В `deploy/docker-compose.yml`
переменная `BACKUP_DATABASE_URL` **обязательна**: без неё compose не запустится, и откат на роль приложения невозможен. Ей выдаются права
`SELECT` на все таблицы и `INSERT, UPDATE` на `backups`. `REPLICATION` выдаётся только для `pg_basebackup`.
Администратор приложения доступа к хранилищу копий не имеет.

```sql
create role kb_backup login password '…';
grant connect on database kb to kb_backup;
grant usage on schema public to kb_backup;
grant select on all tables in schema public to kb_backup;
alter default privileges in schema public grant select on tables to kb_backup;
grant insert, update on backups to kb_backup;
```

## 4. Команды

```bash
# Полная копия
DATABASE_URL=postgres://kb_backup:…@db/kb BACKUP_DIR=/backups STORAGE_ROOT=/var/lib/kb/objects \
  scripts/backup/backup.sh                         # печатает путь к каталогу копии

# Только новые объекты (каждые 5 мин)
STORAGE_ROOT=/var/lib/kb/objects BACKUP_DIR=/backups scripts/backup/backup.sh --objects-only

# Проверка: восстановить во ВРЕМЕННУЮ БД и сверить всё; результат записывается в backups.verified_at
DATABASE_URL=postgres://kb_backup:…@db/kb VERIFY_ADMIN_URL=postgres://kb_verify:…@db/postgres \
  scripts/backup/verify-backup.sh --latest /backups --report /var/log/kb/verify.json

# Восстановление в НОВУЮ БД и НОВЫЙ каталог объектов (никогда поверх рабочей установки)
scripts/backup/restore.sh /backups/kb-20261022T021500Z --create \
  --target-db postgres://kb:…@db/kb_restored_20261022 --target-storage /var/lib/kb/objects-restored

# Объекты для БД, восстановленной на момент времени (PITR)
scripts/backup/restore-objects.sh --db postgres://kb@db-pitr/kb --pool /backups/objects --target /var/lib/kb/objects-pitr

# npm-обёртки
npm run backup            # = bash scripts/backup/backup.sh
npm run restore:verify    # = bash scripts/backup/verify-backup.sh
```

В Docker-образе всё необходимое уже установлено (`pg_dump`/`psql` 16, `jq`, `node`):
`docker compose exec backup /app/scripts/backup/verify-backup.sh --latest /backups`.

### 4.1 Восстановление страницы или пространства из копии (R-BACKUP-015)

Копия (полная или PITR) сначала восстанавливается во **временную** БД и каталог объектов (`restore.sh --create
--target-db … --target-storage …`). Затем команда `restore-pages` сравнивает выбранные страницы с рабочей установкой и
возвращает их **без перезаписи**:

```bash
# Предпросмотр влияния: статус и diff по каждой странице (unchanged / changed / deleted-in-live / missing-in-live),
# сколько вложений отсутствует в рабочей установке. Ничего не меняет.
node apps/server/dist/cli.js restore-pages --source postgres://kb:…@db/kb_restored_20261022 --space <spaceId> --user admin@corp.example
# Применение (одна транзакция, запись в аудит backup.partial_restore):
node apps/server/dist/cli.js restore-pages --source … --page <pageId> --children --user admin@corp.example \
  --apply --label "копия 22.10 02:15" --source-storage /var/lib/kb/objects-restored
```

* Существующая страница (в том числе в корзине) получает состояние из копии **новой версией** в истории
  (`kind = restore`, метка `--label`). Пользователь сравнивает её с текущей и восстанавливает обычным способом.
* Окончательно удалённая страница создаётся заново (новый id) под исходным родителем или под страницей
  «Восстановлено из резервной копии (…)» в своём пространстве. Её вложения возвращаются: из рабочего хранилища, если
  файл там ещё есть, иначе копируются из `--source-storage` с проверкой sha256.
* Документы берутся из снимка и журнала временной БД, поэтому подтверждённые, но ещё не материализованные правки тоже
  восстанавливаются. Проверено тестом `tests/resilience/io-p0-partial-restore.test.ts`.

### Что делает `restore.sh`

1. Проверяет `SHA256SUMS`, sha256 `objects.list` и дампа, а после расшифровки — sha256 открытого текста.
   Неверный ключ или повреждение останавливают восстановление до записи каких-либо данных.
2. Создаёт БД (`--create`). Если БД уже существует или не пуста, работа прекращается: перезапись невозможна.
3. Выполняет `pg_restore --no-owner --no-privileges --exit-on-error -j N`.
4. Сверяет число строк 24 таблиц с манифестом.
5. Копирует объекты из пула и проверяет sha256 **каждого** восстановленного файла. Если цель не пуста,
   работа прекращается.
6. Применяет миграции новой версии (`cli migrate up`), если копия сделана старой версией.
7. Проверяет хеш-цепочку аудита (`cli audit-verify`).
8. Выводит JSON-отчёт с длительностью каждого шага.

### Дополнительные проверки `verify-backup.sh`

* у каждой версии вложения есть строка `blobs`, а у каждого вложения — текущая версия;
* у каждого блоба есть файл в восстановленном хранилище, размер совпадает, sha256 содержимого равен ключу;
* существуют все производные объекты (миниатюры, тайлы);
* `check-docs.mjs`: каждый документ воспроизводится из снимка и журнала без пропусков `seq`, без «висящих»
  структур Yjs и с `last_seq`, совпадающим с журналом; каждая ревизия декодируется;
* временная БД удаляется, результат пишется в `backups.verify_status/verified_at` и в метрику.

## 5. Восстановление после аварии (runbook)

Цель — RTO ≤ 60 мин. Таймер запускается при объявлении инцидента.

1. **Остановить запись.** Остановите приложение или переведите его в режим обслуживания на балансировщике.
   Клиенты продолжат работать офлайн: неподтверждённые изменения останутся в их локальной очереди
   (IndexedDB) и не будут потеряны.
2. **Выбрать точку восстановления.**
   * Если потеряна БД или хост, восстанавливайтесь на последний момент: PITR до конца архива WAL плюс
     `restore-objects.sh`.
   * Если данные испорчены (ошибочная массовая операция, злоумышленник), восстанавливайтесь на время T
     до инцидента. T определяется по `audit_events` и журналу приложения.
   * Если WAL-архив недоступен, восстанавливайтесь из последней полной копии (`restore.sh`).
     RPO в этом случае — до 24 ч.
3. **Восстановить в новый контур** (новая БД или кластер и новый каталог объектов), см. раздел 4 или
   `wal-archive.md` §4.
4. **Проверить.** `audit-verify`, `check-docs.mjs`, а также `verify-backup.sh` — для полной копии.
   Затем выборочно вручную: 5 страниц, их вложения, история, права гостя.
5. **Переключить приложение** на новые `DATABASE_URL`/`STORAGE_ROOT` и запустить его (миграции применяются
   при старте). Проверьте `/readyz`. Клиенты переподключатся и дошлют неподтверждённые изменения.
6. **Задокументировать** фактические RPO/RTO в протоколе инцидента. Старый контур не удаляйте, пока не
   закончится разбор инцидента.

### PITR (отдельный кластер PostgreSQL 16)

Автоматический тест `pitr.test.ts` (организация, вложения, совместные правки) даёт: базовая копия 4,8 МБ — 1,1 с,
переключение и архивирование WAL — 0,35 с, восстановление на T — 1,1 с. До ответа API на восстановленных данных
вместе с `restore-objects.sh` и запуском сервера проходит 1,6 с.

Ручной прогон (ранее): базовая копия 4,6 МБ сделана за 1,1 с. Восстановление на момент T вместе с promote заняло **1,6 с**.
Транзакция-«авария» после T отсутствует, данные до T на месте, цепочка аудита цела. Подробности — в `wal-archive.md` §5.

### Автоматический тест (каждый запуск `npm run test:resilience`)

На небольшой организации тест `backup-restore.test.ts` показывает типичные значения: копия ≈ 1,8 с,
восстановление ≈ 4,8 с, проверка ≈ 5,0 с.

### Оценка RTO для больших объёмов (экстраполяция, не измерение)

Эти числа нужно подтвердить учением на целевой инфраструктуре.

| Объём | Объекты (≈ 50 МБ/с, один поток) | БД (pg_restore -j4, ≈ 50 ГБ/ч с индексами) | Проверки и запуск | Итого |
|---|---|---|---|---|
| 10 ГБ файлов, 2 ГБ БД | ≈ 3,5 мин | ≈ 3 мин | ≈ 5 мин | ≈ 12 мин |
| 100 ГБ файлов, 10 ГБ БД | ≈ 35 мин | ≈ 12 мин | ≈ 10 мин | **≈ 1 ч** — на границе проектного RTO |
| 500 ГБ файлов | ≈ 3 ч | — | — | RTO не выполняется |

Для объёмов > 100 ГБ файлов рекомендуется S3-совместимое хранилище с версионированием и репликацией.
В этом случае объекты не копируются при восстановлении: восстанавливается только БД, а бакет-реплика
подключается как есть. Второй вариант — восстанавливать объекты параллельно в несколько потоков; в
`restore.sh` это пока не реализовано (см. раздел 8).

## 7. Автоматические испытания отказоустойчивости (`npm run test:resilience`)

| Тест | Что доказывает | Требования |
|---|---|---|
| `backup-restore.test.ts` — учение | Контент строится через API: закрытое пространство, группа, редактор, посторонний, вложение, совместные правки, ревизия, неподтверждённый flush. Затем `backup.sh` → `restore.sh` в новую БД и каталог → сервер на восстановленных данных. ## 8. Что НЕ покрыто

* **Секреты и конфигурация.** `SECRET_KEY`, `.env`, сертификаты TLS и ключи шифрования копий в копию не
  входят. Их хранит менеджер секретов (Vault и т. п.) со своей резервной копией. Без исходного `SECRET_KEY`
  восстановленная система работает, но пользователям нужно войти заново. TOTP-секреты хранятся в БД.
* **S3-драйвер не испытан локально** (нет S3/MinIO в тестовом окружении). Путь через `aws s3 sync` в
  `backup.sh`/`restore.sh` проверен только статически. Для S3 предпочтительны версионирование бакета, object lock
  и межрегиональная репликация, а `backup.sh` даёт дополнительную независимую копию.
* **PITR в Docker Compose проверен только статически** (нет Docker-демона). Сценарий PITR автоматически проверяется
  тестом `pitr.test.ts` на временном кластере PostgreSQL 16 с теми же `wal-archive.sh`/`wal-restore.sh`. В compose
  используется упрощённая `archive_command` (cp с атомарным переименованием, без sha256).
* **Восстановление отдельной страницы или пространства из копии** штатного UI не имеет. Используйте
  восстановление в изолированный контур и перенос через архив организации (экспорт/импорт) или историю версий.
  Корзина и версии покрывают типовые случаи удаления без резервной копии.
* **Неподтверждённые локальные изменения клиентов** не входят ни в одну серверную копию. Они хранятся в
  IndexedDB браузера и досылаются после восстановления сервера. Если пользователь очистил данные браузера до
  восстановления связи, они теряются. Пока изменения не подтверждены, редактор показывает статус «только на этом
  устройстве» или «синхронизация», а не «Сохранено».
* **Поисковый индекс** восстанавливается как есть (таблица `search_index`). При сомнении перестройте его
  фоновыми задачами индексации.
* **Объекты восстанавливаются в один поток.** Для очень больших хранилищ см. оценку RTO в разделе 6.
* **Метрики и логи** (Prometheus, журнал) не копируются.
