# План тестовой эксплуатации (пилота) и шлюз запуска

Документ закрывает процессную часть R-PROCESS-052 («До запуска: тестовая эксплуатация, нагрузка, доступность, угрозы
и права, тест восстановления, ручная UX-проверка, регрессии, пилот, план переключения и возврата»). Здесь описано, как
проводится пилот и кто его подписывает. Сам пилот — ручной шаг с участием сотрудников заказчика. Требование
закрывается подписанным протоколом (§9), а не этим документом.

## 1. Цель и объём

**Цель:** подтвердить на реальных пользователях, реальных данных и в целевой инфраструктуре, что база знаний:

* не теряет подтверждённых правок;
* выдерживает рабочую нагрузку;
* восстанавливается из резервной копии в пределах RPO/RTO;
* понятна без обучения.

Кроме того, пилот проверяет, что эксплуатационная команда умеет её вести: алерты, runbooks, выпуск и откат.

| | В объёме пилота | Вне объёма |
|---|---|---|
| Пользователи | 1–2 подразделения, 20–40 сотрудников: 3–5 администраторов пространств, 10–20 авторов, остальные — читатели; хотя бы 2 человека с экранным диктором или увеличением 200 % | Вся организация |
| Содержимое | Реальные регламенты и инструкции пилотных подразделений: импорт из DOCX/Markdown/Confluence-экспорта плюс новые страницы | Конфиденциальные данные выше уровня, согласованного со службой ИБ |
| Функции | Всё по ТЗ: дерево, редактор, совместная правка, файлы и OCR, поиск, права и гости, история, импорт и экспорт, архив | — |
| Инфраструктура | Целевой контур: ≥ 2 экземпляра приложения за nginx (`deploy/nginx.conf`, привязка страницы), PostgreSQL 16 с WAL-архивом, общее хранилище объектов, внешняя копия, мониторинг (`deploy/monitoring/`), CD (`.github/workflows/deploy.yml`) | Нагрузочные стенды |
| Браузеры | Chrome, Edge, Firefox, Safari (macOS/iOS), Chrome Android — то, что реально стоит у пилотной группы | — |

## 2. Сроки

| Этап | Длительность | Содержание |
|---|---|---|
| 0. Вход | 1–3 дня | Шлюз входа (§3), установка в целевой контур через конвейер CD, первичная загрузка содержимого, инструктаж (30 мин), канал обратной связи |
| 1. Ограниченный пилот | 2 недели | 1 подразделение. Ежедневный разбор алертов и обращений. Один плановый выпуск через CD (с откатом на стенде) |
| 2. Расширенный пилот | 2 недели | 2-е подразделение, гости. Учение по восстановлению на копии пилотных данных. Ручная UX-сессия по `docs/UX_ACCEPTANCE.md` |
| 3. Решение | 2–3 дня | Отчёт по критериям (§4), подписание (§9) или повтор этапа |

Минимальная продолжительность — **4 недели** рабочих дней. За это время должны пройти хотя бы один выпуск через
CD, одно учение по восстановлению и один полный месяц ротации копий в части ежедневных и еженедельных.

## 3. Шлюз входа (что должно быть сделано до пилота)

| Проверка | Доказательство | Состояние на 23.10.2026 |
|---|---|---|
| Регрессия: unit, integration, resilience, E2E — зелёные на релизной ветке | `npm run qa:run`, CI (`.github/workflows/ci.yml`) | выполняется в CI на каждом коммите |
| Нагрузка: подтверждение правки p95 ≤ 500 мс при целевой нагрузке | `scripts/load/collab-load.mjs` на выделенном стенде | **не выполнено** на целевом железе (PERF-D4, `docs/RELEASE_READINESS.md` §6.1) |
| Длительная работа без утечек | `scripts/load/soak.mjs`, `docs/PERFORMANCE.md` «Soak» | прогон 1 ч 36 мин в среде разработки (0 потерь, утечек дескрипторов и соединений нет); многочасовой (суточный) прогон **не выполнен** — ручной шаг на стенде пилота до входа |
| Отказоустойчивость: сеть, БД, рестарт, несколько экземпляров | `tests/resilience/network-faults.test.ts`, `multi-instance.test.ts`, `crash-restart.test.ts`, `db-connection-loss.test.ts` | автотесты зелёные |
| Доступность (a11y) | `tests/e2e/a11y.spec.ts` (axe), ручная проверка с диктором | автоматическая — да, ручная — на этапе 2 |
| Угрозы и права | `docs/SECURITY.md`, `docs/ASVS.md`, SAST/DAST, ACL-тесты | пентест независимой командой — открыт (SEC-L2) |
| Восстановление | `npm run restore:drill`, `docs/drills/` | учение проведено в среде разработки; на целевом контуре — этап 2 |
| Конвейер выпуска и отката | `tests/integration/deploy-pipeline.test.ts`, пробный прогон workflow | в целевом контуре — этап 0 |

(«принимаем и проверяем в пилоте»).

## 4. Критерии успеха

| # | Критерий | Порог | Как измеряется |
|---|---|---|---|
| K1 | Потери подтверждённых правок | **0** | Обращения пользователей; алерт `KbCollabPersistFailures`; сверка журнала `doc_updates` с ревизиями (`npm run audit-verify`, `GET /api/v1/admin/health`) |
| K2 | Доступность в рабочее время | ≥ 99,9 % | `up{job="kb"}` и внешний HTTP-зонд `/readyz`; плановые окна не учитываются |
| K3 | Подтверждение правки (сервер) | p95 ≤ 500 мс, p99 ≤ 1 с | `kb_collab_persist_seconds`, панель Grafana |
| K4 | Задержка ввода у пользователей | p95 ≤ 50 мс | `kb_client_input_latency_ms` (телеметрия браузеров) |
| K5 | Неотправленные изменения | нет очередей старше 5 мин | `kb_client_unsynced_queue_age_seconds`, алерт |
| K6 | Утечки | нет срабатываний `KbMemoryLeakSuspected`, `KbHeapLeakSuspected`, `KbFileDescriptorLeak`, `KbDbPool*` | Alertmanager |
| K7 | Резервные копии | ежедневная копия и еженедельная проверка без пропусков; учение: RPO ≤ 5 мин, RTO ≤ 4 ч | `kb_backup_age_seconds`, протокол учения в `docs/drills/` |
| K8 | Выпуск и откат | ≥ 1 выпуск через CD без ручных шагов; откат проверен на стенде | `deploy-report.json` |
| K9 | Блокирующие дефекты | 0 открытых critical/high к концу пилота | `docs/qa/DEFECTS.md` |
| K10 | Удобство | SUS ≥ 70; ≥ 80 % участников выполнили сценарии §2 `UX_ACCEPTANCE.md` без помощи | Анкета в конце этапа 2 |

## 5. Мониторинг во время пилота

* Алерты `deploy/monitoring/prometheus-alerts.yml` направляются в канал дежурного. Критичные дублируются по
  телефону с 9:00 до 19:00.
* **Ежедневно в 10:00, 15 минут:** разбор алертов и обращений за сутки, состояние копий, отставание индекса,
  ошибки клиентов (`kb_client_errors_total`). Итоги записываются в журнал пилота.
* **Еженедельно:** отчёт по K1–K9, тренды памяти и дескрипторов за неделю (те же наклоны, что в soak-тесте),
  рост БД и хранилища.
* Журналы приложения хранятся не меньше 30 дней. Они без содержимого документов и секретов
  (`docs/OPERATIONS.md` §6).

## 6. Обратная связь

* Каналы: отдельный чат пилота и почтовый ящик. В сообщении об ошибке приложение показывает номер (`correlationId`):
  по нему эксплуатация находит запись в журнале. Плюс недельный опрос из 3 вопросов.
* Сортировка — в течение рабочего дня: дефект записывается в `docs/qa/DEFECTS.md` с важностью и регрессионным
  тестом при исправлении (R-QA-038), предложение — в бэклог.
* Сроки исправления: critical — исправление или обход в течение суток (выпуск через CD), high — до конца этапа,
  остальные — по плану.
* Каждую пятницу участникам отправляется короткая сводка: «что исправлено, что в работе».

## 7. План переключения и возврата

**Переключение (в начале пилота).** Старая система (файловые папки, вики) остаётся доступной только для чтения.
Содержимое пилотных подразделений импортируется. По отчёту импорта проверяются расхождения: ссылки, вложения,
таблицы. Ссылки на старую систему ведут на новые страницы.

**Возврат в старую систему**, если пилот остановлен по критериям §8:

1. Объявить заморозку изменений (баннер, письмо). Последние правки сохраняются: клиенты досылают очередь при
   открытой вкладке.
2. Экспортировать всё содержимое: архив организации (`kb-archive v1`), читаемый без приложения: Markdown, вложения,
   история. Плюс Markdown или DOCX по пространствам — для импорта в старую систему.
3. Снять финальную копию (`backup.sh` + `verify-backup.sh`) и хранить её не меньше срока, согласованного с
   владельцем данных.
4. Вернуть старой системе запись. Новую систему перевести в режим только чтения (отзыв прав на запись) на срок
   сверки.

**Возврат версии внутри пилота** (неудачный выпуск) выполняется автоматически конвейером CD: миграции откатываются,
предыдущий образ возвращается (`docs/OPERATIONS.md` §3.1). Если откат не удался — runbook §7.11.

## 8. Остановка пилота

Пилот приостанавливается, исправляется и этап повторяется, если:

* потеряна подтверждённая правка (K1);
* данные стали видны пользователю без прав;
* восстановление из копии не удалось;
* простой больше 4 часов подряд.

Решение принимает владелец продукта вместе с ИБ.

## 9. Роли и подписание

| Роль | Ответственность |
|---|---|
| Владелец продукта (заказчик) | Объём, решение о переходе к этапам, итоговая подпись |
| Руководители пилотных подразделений | Участники, сценарии, оценка удобства |
| Эксплуатация (ops) | Установка, мониторинг, копии, учение по восстановлению, выпуски |
| Информационная безопасность | Права, гости, журналы, пентест, допуск данных |
| Команда разработки | Разбор дефектов, исправления, регрессионные тесты |

|---|---|---|---|
| K1 … K10 (§4) | | | |
