# Архитектура корпоративной базы знаний

Документ описывает фактическую реализацию в этом репозитории (а не намерения). Источник требований — `SPECIFICATION.md`, реестр — `docs/requirements/registry.yaml`, статус — `docs/REQUIREMENTS_TRACEABILITY.md`.

## 1. Общая схема

```
Браузер (React 18 + Tiptap/ProseMirror + Yjs)
  │  HTTPS: REST /api/v1/*  (cookie-сессия + CSRF-заголовок)
  │  WSS:   /api/v1/collab/:pageId  (совместное редактирование, бинарный протокол)
  │  WSS:   /api/v1/events          (уведомления об изменениях: только ID, данные — через REST с проверкой прав)
  ▼
Сервер приложений Node.js 22 (Fastify 5), один процесс = API + WebSocket + фоновые задачи
  ├─ PostgreSQL 16 — единственный источник истины: метаданные, права, журнал CRDT-обновлений,
  │   снимки документов, версии, поисковый индекс (FTS + pg_trgm), очередь задач, аудит (хеш-цепочка)
  ├─ Хранилище объектов — файлы по SHA-256 (локальная ФС с fsync или S3-совместимое)
  └─ LISTEN/NOTIFY PostgreSQL — шина событий между экземплярами (Redis не нужен)
```

Монорепозиторий (npm workspaces):

| Пакет | Назначение |
|---|---|
| `packages/shared` | Общий для браузера и сервера код: схема документа (Tiptap-расширения), конвертер Markdown ↔ документ, протокол и клиент совместного редактирования, модель прав, сортировочные ключи |
| `apps/server` | API, WebSocket-хаб, ACL, импорт/экспорт, OCR, архив организации, фоновые задачи, миграции |
| `apps/web` | SPA: оболочка, дерево, редактор, панели, администрирование |
| `tests/*` | unit, integration (реальный PostgreSQL), resilience, e2e (Playwright/Chromium) |

## 2. Модель данных (основное)

* `organizations`, `users`, `sessions`, `api_tokens`, `groups` (отделы с вложенностью и обычные группы), `group_members`.
* `spaces` (пространства, включая личные), `pages` (дерево: `parent_id` + дробный `sort_key`), `page_ancestors` (замыкание для быстрых проверок наследования прав и путей).
* `grants` — выдачи прав (пространство/страница → пользователь/группа/вся организация; уровни none/view/comment/edit/full + флаги экспорт/скачивание/публикация/шаринг, сроки действия), `acl_epoch` — версия прав для инвалидации.
* Документы: `doc_updates` (append-only журнал CRDT-обновлений с `op_id` для идемпотентности), `doc_state` (снимок, материализованный JSON, plain-text, `generation`), `page_revisions` (версии), `page_events` (журнал правок).
* Файлы: `blobs` (содержимое по SHA-256), `attachments` + `attachment_versions`, `upload_sessions` (докачка), `blob_derivatives` (превью, тайлы), `ocr_results`.
* `comments`, `approvals`, `notifications`, `favorites`, `recent_views`, `templates`, `collections` (реестры), `search_index`, `jobs`, `outbox`, `idempotency_keys`, `audit_events` (триггер запрещает UPDATE/DELETE), `backups`, `invitations`, `share_links`, `access_requests`.

Миграции — SQL-файлы `apps/server/migrations/NNNN_*.sql` с секциями up/down, применяются под advisory lock с контрольной суммой (`npm run db:migrate`).

## 3. Документ и совместное редактирование

* Каноническая схема — ProseMirror-схема из `packages/shared/src/editor/extensions.ts`; одна и та же на клиенте и сервере. Каждый блок имеет стабильный `id` (якоря, комментарии, история блоков, ссылки на блок, поиск «перейти к совпадению»).
* Состояние документа — Yjs `Y.Doc` (фрагмент `default` = содержимое, `Y.Text title` = заголовок, чтобы заголовок тоже сливался при одновременной правке).
* Протокол (`packages/shared/src/collab-protocol.ts`): HELLO(вектор состояния) → SYNC(недостающее) → UPDATE(opId, update) → **ACK только после фиксации транзакции в PostgreSQL** / NACK; REMOTE — чужие изменения; AWARENESS/PRESENCE — курсоры и присутствие (идентичность выдаёт сервер); ACCESS — смена прав «на лету».
* Сервер (`apps/server/src/collab/hub.ts`): на каждое обновление — проверка прав, валидация по схеме (невалидное отклоняется, у клиента — перезагрузка состояния), запись в `doc_updates` с идемпотентностью по `op_id`, затем ACK и рассылка. Периодический flush материализует JSON/текст, ведёт журнал правок, авто-версии (раз в 5 минут активной правки) и компактирует журнал.
* Клиент (`packages/shared/src/collab-client.ts`, `apps/web/src/sync/*`): локальная реплика документа в IndexedDB (`y-indexeddb`), отдельная очередь неподтверждённых операций (IndexedDB), пакетирование, повтор с экспоненциальной задержкой и джиттером, повторная отправка после переподключения (идемпотентно). Индикатор «Сохранено» показывается только при пустой очереди после ACK.
* **Резервный канал** (`packages/shared/src/collab-http.ts`, `apps/server/src/collab/tunnel.ts`): если WebSocket не устанавливается дважды подряд (или открывается, но не доставляет SYNC — прокси), клиент переходит на HTTPS long polling `/api/v1/collab/:pageId/tunnel` с теми же бинарными кадрами; хаб обрабатывает туннель как сокет (права, валидация, ACK после commit), кадры сервера подтверждаются клиентом (`?after=`) и не теряются при обрыве ответа. Раз в 5 минут клиент снова пробует WebSocket. **Backpressure**: не более 32 операций / 4 МБ без подтверждения, отправка приостанавливается при заполненном буфере сокета; операция уходит на сервер только после записи в локальный журнал IndexedDB.
* **Конфликты удаления/переноса** (`apps/web/src/editor/extensions/conflictGuard.ts`): если чужое изменение удалило или перенесло (удаление+вставка копии) блок, который пользователь правил, его версия сохраняется на сервере как конфликтная копия (`page_events.conflict_copy`) и возвращается одним действием.
* **Поколение документа** (`doc_state.generation`): локальные реплики и очередь ключуются им. При пересоздании истории документа вне CRDT (восстановление из архива) старая реплика браузера не может слиться с новой историей и задвоить текст.
* Редактор монтируется только после загрузки локальной реплики и первой синхронизации (или короткого таймаута офлайн): иначе нормализующие плагины записали бы в CRDT служебные пустые блоки.

## 4. Права доступа

`apps/server/src/acl/engine.ts`. Субъекты пользователя = он сам + группы + родительские отделы + «вся организация» (кроме гостей). Применимые выдачи: пространство и все предки страницы до ближайшей границы наследования (`inherit_permissions = false`). Явный запрет (`none`) побеждает. Политика пространства ограничивает действия (режим публикации, экспорт/скачивание, гости). Недоступные страницы отдаются как 404 (без утечки существования), в дереве и поиске фильтруются до выдачи результатов. При изменении прав поднимается `acl_epoch`, открытые WebSocket-сессии перепроверяют доступ и переходят в режим чтения или закрываются. Перед расширением аудитории сервер требует подтверждения и показывает, кто получит доступ.

## 5. Файлы, изображения, OCR

Загрузка: multipart (малые) или докачиваемая по кускам (`/api/v1/uploads`, смещения, проверка SHA-256). Проверки: сигнатуры исполняемых файлов, санитизация SVG, опционально ClamAV. Хранение по SHA-256 с fsync+rename (дедупликация). Производные: превью 512/2048 px (WebP) и тайлы deep-zoom (512 px) для очень больших изображений — просмотрщик не декодирует оригинал целиком. OCR — tesseract.js с локальными моделями rus/eng, результаты индексируются и могут быть исправлены пользователем.

## 6. Поиск

Таблица `search_index` (FTS russian+english с весами, trigram для опечаток), варианты запроса: неверная раскладка, транслитерация, синонимы. ACL применяется до подсчёта и сниппетов. Фильтры: пространство, автор, статус, даты, тип совпадения (текст/изображения/файлы). Возвращается первый совпавший блок для перехода, «возможно, вы имели в виду».

## 7. Импорт/экспорт и архив

Импорт DOCX (mammoth + стили), Markdown/ZIP (remark, безопасная распаковка: zip-slip/zip-bomb), HTML (санитизация), CSV/XLSX (определение кодировки, разделителя, типов) — двухфазно: анализ с отчётом → атомарная фиксация в одной транзакции с ключом идемпотентности. Экспорт: Markdown (+ZIP с вложениями и относительными ссылками), DOCX, HTML, PDF (Chromium). Архив организации (`kb-archive v1`): манифест, метаданные, содержимое, версии, файлы, контрольные суммы, README — читается без приложения; восстановление с пробным прогоном, сопоставлением пользователей и пост-проверкой.

## 8. Клиент

React 18 + react-router + TanStack Query (кеш запросов), zustand (UI-состояние). Ленивые маршруты; конвертер Markdown и Mermaid загружаются по требованию (стартовый бандл ≈140 КБ gzip, редактор ≈410 КБ gzip). Service worker кеширует оболочку приложения (без кеширования API), чтобы локальные копии документов открывались без сети. Дизайн-токены — `apps/web/src/styles/tokens.css` (светлая тема — эталон, тёмная переопределяет те же токены).

## 9. Безопасность (кратко, подробно — `SECURITY.md`)

Пароли — argon2id; TOTP; OIDC; сессии в httpOnly cookie + CSRF double-submit; rate limit на вход; CSP/helmet; санитизация HTML/SVG; ссылки — только безопасные схемы; файлы отдаются с `Content-Disposition` и sandbox-CSP; аудит — append-only с хеш-цепочкой и проверкой `npm run audit-verify`.

## 10. Масштабирование

Экземпляры приложения не хранят состояния между запросами, кроме живых документов в памяти хаба. Обновление,
принятое любым экземпляром, попадает в общий журнал PostgreSQL. Остальные экземпляры догоняют журнал по NOTIFY и
учитывают разрывы последовательности. События дерева, страниц, прав и комментариев идут через ту же шину
(`lib/events.ts`). Для нескольких экземпляров нужно общее хранилище объектов: каталог на общем томе или
S3-совместимое хранилище.

**Присутствие, курсоры и HTTP-туннель резервного канала хранятся в памяти экземпляра.** Поэтому балансировщик
направляет все запросы одной страницы на один экземпляр: `deploy/nginx.conf`, upstream `kb_collab`, консистентный
хеш по id страницы. URL туннеля содержат id страницы (`/api/v1/collab/:pageId/tunnel/:id/…`), чтобы привязка
работала и для него. При отказе экземпляра его страницы переходят на соседний. Клиенты переподключаются (backoff,
liveness по PING/PONG) и досылают неподтверждённые правки идемпотентно по `opId`.

Проверено тестом `tests/resilience/multi-instance.test.ts`: два процесса на одной БД и общем каталоге объектов за
балансировщиком (`tests/support/lb-proxy.ts`). Совместная правка через разные экземпляры, события и файлы между
экземплярами, SIGKILL экземпляра во время набора — 0 потерь и 0 дублей. Полное присутствие и HTTP-туннель
работают при привязке по странице. Без привязки присутствие разделено по экземплярам; это задокументированное
ограничение, а не потеря данных.
